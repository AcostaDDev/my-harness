# Security policy

My Harness runs locally and can launch development tools with access to
registered projects. CLI permissions and cooperative checks have limits; use
only projects and tools you trust.

The first public release is being prepared. There are no published security
support guarantees or maintained release branches yet. Include the exact package
and CLI versions in a report so maintainers can assess the affected behavior.

Use GitHub's private vulnerability reporting from this repository's security
tab, then **Report a vulnerability**. The repository owner must enable this
feature before the public opening; adding this file does not enable it. If the
button is unavailable, open an issue asking for a private reporting channel,
without vulnerability details, and wait for the maintainer's instructions.

In a private report, describe the affected version, impact, prerequisites,
reproduction steps and a minimal synthetic proof of concept. Remove credentials,
private source, personal paths, logs and operational data that are unnecessary
to understand the problem. Do not post exploit details in public issues or pull
requests before coordinating disclosure with the maintainer.

Reports are reviewed as time permits. There is no guaranteed response deadline
or bug bounty. Reporting a vulnerability does not authorize testing against
someone else's projects, accounts or machines.

See GitHub's [private reporting guide](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/report-privately).
