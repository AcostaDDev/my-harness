# P002-T030 — D321 feasibility and qualification proposal

Part of the [T030 review record](P002-T030-contracts.md). [D321](../DECISIONS.md#d321--verifiable-prevention-of-raw-project-documentation-reads)
requires technical prevention for each admitted profile. D322 controls external compatibility export selection.
They are independent. D064/D065 and T027 describe older, differently scoped evidence.

## Preferred boundary

Use a disposable, isolated guest for each invocation or validation command, with a verified positive
projection of code/build/test inputs. Provide no host filesystem, host Git store, host process namespace,
credentials, shared clipboard, host mounts or inherited host descriptors. A trusted host controller outside
the guest owns selection, capture, DB, Git, checkout lock and the evidence broker. A read-only base image
contains pinned runtime/tools. Each invocation gets only a measured input tree and bounded scratch. Writer
stages get a writable code overlay. Read-only stages get only disposable writable scratch. All subprocesses
and native file tools see the same boundary. Only validated outputs and declared code deltas cross out.
No reusable workspace, user home, cache or daemon crosses epochs. For the first feasibility cell, propose
a headless ARM64 Linux guest on the inspected ARM64 macOS host with no guest NIC and a dedicated
host/guest socket transport. A host controller sends the measured input bundle and checks a nonce-bound
ready receipt before enabling per-invocation tool and provider routes. The host keeps provider credentials.
The provider mediator must validate the exact native protocol and enforce a fixed provider destination;
it never accepts CONNECT, arbitrary DNS destinations or remote tool invocation. This is a candidate to
test, with exact runtime and client artifact availability still to establish.

The guest has no general outbound routes. Expose a dedicated scoped tool transport to the host broker and,
if native inference needs network, a separate narrowly mediated inference transport. It must support the
actual client and credential flow without arbitrary web search, URLs/proxies, host service access, shared
credentials/cache or generic host RPC. A guest requiring network-dependent builds refuses admission. Verified
offline dependencies may enter through the same projection. The host does not execute guest hooks or take
filesystem paths from tools. Establish an exact guest/runtime/client/provider transport before calling the
design feasible. This record does not select a qualified OS, client version, provider or dependency.

The guarantee assumes a trusted host kernel/hypervisor, curator/controller, runtime image, owner and
classification metadata. It concerns protected source bytes and their actual copies reachable through admitted
routes. A malicious host user or compromised boundary is outside it. Matching hashes alone cannot prove
that semantically equivalent copies or mixed content are absent. Ambiguous provenance must exclude that input
or refuse the stage, and model knowledge or reconstruction independent of raw source reads is outside the
claim. After-the-fact detection is not protection.

## Protected selection and revalidation

Before creating any guest input mount, an authorized source-selection operation seals `protected-selection-1`:
project or pre-adoption intake identity, monotonic epoch, source IDs, class, exact immutable capture digest/size,
locator and provenance, permitted tool ranges/purposes, retained aliases/lineage, tree/head and projection
inventory digest. Locators stay in the trusted controller. Capture via verified descriptors/objects with no
unapproved link traversal, bind identity and bytes, and reject races before seal. Read committed bytes by
pinned tree/object, never through a filtered live checkout. Capture selected local and external original bytes
separately from committed bytes. Mismatch after review requires new capture and confirmation.

Classify the whole build closure before exposing any of it. A positive entry binds immutable content, mode,
exact path, origin and classification. Admit code, tests, runtime/deps and explicitly classified noncanonical
documents. The inventory tracks known copies, generated dependencies and mixed inputs by provenance. Exact
digest matching is an additional guard against byte copies. Require trusted classification of unknown or
changed inputs. Refuse path/case/normalization collisions and nonregular objects. Approved link targets can
only enter as fresh, independently eligible regular bytes. Export ownership separately controls paths allowed
for generation. No accepted revision or ownership is needed for protection.

| Route or source class | Prevention and verification |
|---|---|
| Selected originals, unowned/unadopted, external, later owned | Exact capture and independent selection; host originals absent in guest regardless of name or ownership; tool exposure only |
| Temporary copies, copied HEAD, retained originals, caches, snapshots, archives, DB/evidence and companions | No host directory mounts or legacy copied HEAD. No guest home/cache reuse. Controller materializes only approved regular inputs; every known copy/source descendant tracked or excluded |
| Aliases, symlinks, hardlinks, case/normalization and races | Do not project link objects, worktree indirections or nonregular nodes. Compare stable descriptor/object identity and bytes; refuse collisions; guest output intake also rejects links/devices/unsafe names |
| Git objects/history, index/refs, worktree metadata, reflogs, submodules, alternates, hooks | No object store or remotes in guest. Guest never shares host worktree/ref/index. Approved code and bounded typed commit metadata only; commands needing unrestricted Git history refuse |
| Client/global/nested instructions, imports, generated wrappers | Canonical rules enter as sealed context. Exclude project/ancestor instructions, D322 views, personal/client home configuration, imports and caches. Fixed isolated configuration. Disable autoload as defense in depth; qualify startup and deliberate tool access independently |
| Mixed source/code file | Exclude entire file. Only admit a reviewed deterministic derived artifact without protected spans/structure if its build semantics are verified. If exact validation needs the original mixed bytes, refuse that stage/profile |
| Code/build/tests and noncanonical docs | Allow positively classified inputs regardless of Markdown extension. Verify actual build/test against the projection and exact candidate |
| Scoped tools | Host verifies caller, live authorization, epoch, source/range and budget, reads immutable capture, receipts exact exposure. No path or directory discovery |

At a selection/authority transition seal a successor epoch, verify coverage under the existing writer
and invocation fences. Reverify image/transport/qualification, input tree and selection digests and authority
before materialization/attach/spawn/GO, candidate transfer, validation/review capture and host Git effect.
Compare current trusted metadata rather than remounting. A running guest keeps immutable old inputs and cannot
obtain new source bytes with its old lease. Close revoked tool capabilities and settle under the original
authority records. A proposed transition that would classify a live guest input as newly protected must wait
for observed teardown (or separately authorized existing revocation/cancellation that removes access).
Prior exposure is historical; no implicit cancellation or rewriting. Missing cleanup proof refuses transition
and reuse. Adoption, conversion or ownership loss do not reduce protection. Explicit removal needs separate
confirmation/impact preview, cannot remove owned/control/instruction protection or uncover an overlapping
protected identity/copy. Old captures stay protected.

## Code effects and recovery

Guest workspace materializes admitted paths at the sealed tree. A guest executor returns a sorted manifest of
regular-file additions/replacements/deletions with expected old/new digests/modes in the typed allowed scope.
Host validates and stages only those exact bytes against the expected baseline, with protection and permission
rechecked. Review and validation receive a separately measured projection of the exact same candidate.
Missing required inputs or metadata refuses the stage. Builds needing version identity may receive only
bounded typed base/candidate metadata, otherwise the profile cannot be qualified for that build.

Git effects remain host-side under the existing checkout lock and D298/T014/T015/D294 ownership. Combine
candidate deltas and separately sealed mechanical documents with exact tree/parent/index/ref, allowed modes,
review/code digest, manifest, ref CAS and deterministic commit/archive/tag receipts. Use guarded host plumbing
without guest hooks, filters, remotes, submodules or object sharing. Reconcile only a possibly applied sealed
effect from verified observations. Never patch around a changed ref, relaunch an uncertain model call or
accept an agent statement as a Git effect.

4. Record commands, synthetic inputs, hashes, byte/receipt/liveness evidence, failures and refused cells.
   If the transport or required offline build cannot work, mark that profile incompatible. If no acceptable
   scope is feasible, return that incompatibility to the owner. No cooperative fallback.

### Offline real guest

- **Input to request.** An owner-approved local boot bundle for a disposable Linux ARM64 guest
  (image and any separate kernel/initrd, with offline build/test tools), plus the matching macOS
  ARM64 launcher/controller, policy and Linux guest endpoint for the dedicated channel. Supply paths,
  provenance, exact versions, hashes and the launch/cleanup entry points. For an Apple Virtualization
  candidate the manifest must bind an empty NIC list, the socket endpoint and port, no shared host
  resources and disposable guest storage. If these artifacts must be prepared or supplied externally,
  record the exact artifacts and obtain separate authorization for that step. Client/provider artifacts
  and credentials are unnecessary for the offline run.
- **Execution limit.** One approved synthetic project in disposable host storage and fresh guest state
  for each protocol case. Bound each case by a recorded timeout and cleanup deadline. Transfer only the
  measured input bundle. Enable scoped broker access after validating the nonce-bound ready receipt.
  No provider route, native client, host checkout mount, guest NIC, inherited host descriptors, host
  Git store or production data. Inspect the sealed configuration before boot and corroborate the
  device, mount, process and route inventory from both sides before enabling scoped tool access.
- **Positive evidence.** Use the synthetic inputs in [the existing component probe](P002-T030-fixtures.md#offline-boundary-probe)
  as the reference for projected `app.sh`, `test.sh`, eligible `notes.md`, denied canaries, bounded
  source slice and the host Git comparison. `probe.py` at the inspected baseline has SHA-256
  `96c2fd9d41e6e9acc73761f753badd29ae8208023464dda4365f261622001ff1`. Its macOS sandbox commands
  are component checks. On Linux, compile and execute a minimal synthetic program with the pinned
  offline compiler in guest scratch, run the projected syntax check and test, and retest the exact
  returned candidate in a separate measured projection. Verify the bounded slice through the live
  scoped endpoint with a receipt binding caller, epoch, source and exposure digests and exact range.
  On the host, compare the exact code-plus-sealed-document tree to an independently staged reference,
  record commit/parent/ref and CAS outcome, preserve the protected blob and prove stale CAS refusal.
- **Negative and lifecycle evidence.** For every route in the prevention table and protocol step 2,
  record the attempted access, the pre-access denial or absent route and zero protected direct bytes.
  Include deliberate child-process access, nested startup, host IPC/egress/descriptors and the historical
  blob. Inject binding drift before materialization and GO. Revoke the old lease during a live invocation
  and verify that it cannot read again. Verify that a newly protected live input holds the transition until
  teardown is observed. Record independent process and route observations on normal exit, cancellation
  and parent loss/EOF. Exercise unresolved cleanup and same-intent reconciliation without relaunch.
- **Evidence record.** Keep exact commands, versions, input and policy hashes, observed results and refused
  cases alongside the receipts and teardown observations. Keep the record synthetic and free of credentials.
- **Stop rule.** Refuse admission on missing provenance, a mismatched manifest, any unaccounted input
  or an unverified isolation setting. Stop on protected byte exposure, an unexpected route, a failed
  positive control or missed deadline. Revoke access, record the failure and preserve the evidence.
  Unresolved cleanup holds transition and reuse. End after the recorded cases and verified cleanup.
  A passing offline run supplies guest evidence only.

### Later native transport

- **Input and execution limit.** After offline success, request separate authorization for one exact
  Linux ARM64 client/version and broker/inference transport, including the provider destination,
  configured model/effort, role/stage and bounded calls and timeouts. Codex `0.165.0` is conditional
  on an approved Linux ARM64 artifact. Recheck the offline bindings against the native manifest.
  Add only the fixed-destination, protocol-validating inference mediator over the dedicated channel.
  Keep credentials on the host and preserve the no-NIC boundary. Use the disposable synthetic project
  for the read-only reviewer and writer cells, plus Bootstrap and a separate no-project scratch case
  on that same transport. Scratch has no project mount, authority or source capability.
- **Required evidence.** Show the real provider path works for the authorized cases. Record the exact
  tuples, typed outputs and observed provider/tool events. Verify D321 through native file tools, shell,
  subprocess and startup as applicable, including bounded source reads with receipts only in admitted
  project cells and independent teardown evidence. For each scoped reader/writer cell record all
  [MC1–MC7 results](P002-T027-security-provider-audit.md#mc1mc7-client-profile-and-transport-matrix),
  preserving MC5's read-only scope and the separate writer policy. Record Bootstrap and scratch
  viability separately, including absence of project access in scratch. Historical or synthetic results
  cannot fill unknown native cases. [T027's pending cells](P002-T027-security-provider-audit.md#g15-remainder-release-blockers-and-residual-risk)
  retain their original scope, including RB1–RB4. T035 still owns actual profile/stage qualification.
- **Stop and disposition.** Apply the offline stop rules and stop if the client requires general egress,
  guest credentials, a host share or another unapproved route, or if any required native result remains
  unknown. End after the authorized cases. Revoke the mediator and tool routes and observe teardown.
  Refuse an incompatible profile and return the exact artifact or setting, observed failure and unmet
  requirement to the owner to choose another candidate or leave the scope unsupported. If only the
  observed macOS binaries are available, supply a compatible guest client artifact or review a different
  exact client. No weaker fallback.
  Owner acceptance of the scope actually demonstrated follows evidence review. It is separate from
  authorization to execute and from the [explicit design decision](P002-T030-contracts.md#owner-decisions-required).
